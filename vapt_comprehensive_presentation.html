🛡 Foundational Cybersecurity Concepts

What is Penetration Testing & Why is It Crucial in Modern Cybersecurity?

Moving beyond theoretical vulnerabilities to prove real-world exploitability and business risk

🔍 What is Penetration Testing (Ethical Hacking)?

An authorized, simulated cyberattack performed against an organization's computer systems, networks, or applications to evaluate security posture by discovering and safely exploiting vulnerabilities.

VA vs. PT: Understanding the Key Difference
  • Vulnerability Assessment (The "What"): Automated, broad inventory of potential weaknesses, unpatched software, and configuration flaws.
  • Penetration Testing (The "So What?"): Active, goal-driven exploitation demonstrating how an adversary can pivot, escalate privileges, or exfiltrate critical data.
🛡 Why Penetration Testing is Crucial
  • Proves Real-World Exploitability: Filters scanner noise and false positives by confirming which vulnerabilities threat actors can realistically weaponize.
  • Discovers Chained & Complex Attack Paths: Uncovers logic bugs and lateral movement vectors that automated scanners cannot detect on their own.
  • Mandatory Compliance & Standards: Required by major regulatory frameworks including PCI-DSS 4.0, ISO/IEC 27001, SOC 2 Type II, and HIPAA.
  • Validates Incident Response & Blue Teams: Tests whether organizational SOC analysts, SIEM alerts, and endpoint detection actually catch active adversarial activity.
💡 The Core DevSecOps Takeaway

Security is not the absence of vulnerabilities, but the capability to detect, prioritize, and remediate exploitable flaws. Combining continuous network scanning with centralized vulnerability management ensures that discovered exposure points are validated, assigned, and resolved under strict SLAs before malicious actors exploit them.

⚡ Scanner Architecture & IPC Design

Why Native Greenbone OpenVAS vs. Containerized Scanning?

Analyzing why native host execution was selected over a monolithic container deployment

⚡ 1. Raw Socket Transmission

Direct Hardware Access: Vulnerability scanning relies on raw TCP SYN packets, dynamic banner grabs, and precise round-trip timing.

No NAT Masquerading: Docker bridge networks (docker0) mask source IPs, fragment UDP packets, and produce false positives during OS fingerprinting.

🔗 2. UNIX Socket Throughput

High-Speed Local IPC: Daemon communication between gvmd and ospd-openvas takes place directly over /run/ospd/ospd-openvas.sock.

Zero Network Latency: Eliminates virtual bridge serialization, port forwarding bottlenecks, and TLS overhead when processing 85,000+ NVTs.

💾 3. Feed Storage Stability

Direct Block I/O: Daily community feeds write directly to local NVRAM and filesystem blocks (/var/lib/gvm/ and /var/lib/openvas/).

No Volume Contention: Avoids overlay filesystem locking penalties and orphaned feed-update.lock deadlocks common in multi-container mounts.

🖊 Architectural Compromise Rejected: Why Not Full Docker?

The Hybrid Architecture Advantage: We rejected running OpenVAS inside Docker because container network bridges mask target IP addresses and degrade raw scanning accuracy. Our hybrid architecture combines the best of both worlds: native host execution for the scanner to preserve bare-metal network fidelity, paired with Docker containerization for DefectDojo's web and database microservices.

🔩 Empirical Systems Engineering Case Study 1

Resolving Unset Feed Owner UUID & Missing Port Lists

Overcoming relational database foreign-key constraints in Greenbone Vulnerability Manager

❌ The Blocker: Unset Feed Owner UUID

Error: "The feed owner is currently not set. This issue may be due to the feed not having completed its synchronization."

Why It Happened: In Greenbone GVM, feed data (port lists, scan configs) are stored as relational rows in PostgreSQL. PostgreSQL requires an owning user UUID so security permissions can be enforced. Without an owner, the manager refuses to insert rows.

✅ The Solution: Automated Feed Owner Binding
# Query admin user UUID and bind to internal GVM feed setting kali@kali:~$ sudo runuser -u _gvm -- gvmd --modify-setting 78eceaec-3385-11ea-b237-28d24461215b --value $(sudo runuser -u _gvm -- gvmd --get-users --verbose | grep admin | awk '{print $2}')

The Purpose: Automatically binds our active admin UUID into setting 78eceaec..., granting the daemon permission to instantiate feed objects.

❌ The Blocker: Missing Default Port List

Error: "Failed to create a new Target because the default Port List is not available."

Why It Happened: The scanner downloaded the port list XML files, but gvmd had not yet parsed the XML into PostgreSQL tables (All IANA assigned TCP, All TCP and Nmap top 100 UDP).

✅ The Solution: GVMD-Data Sync & Rebuild
kali@kali:~$ sudo greenbone-feed-sync --type gvmd-data kali@kali:~$ sudo runuser -u _gvm -- gvmd --rebuild-gvmd-data=all

The Purpose: Forces gvmd to read the raw XML port definitions and populate the relational tables, instantly unlocking Target creation in the GUI.

🔩 Empirical Systems Engineering Case Study 2

Resolving Mutex Lock Contention & Missing Scan Configs

Managing asynchronous daemon locks and verifying OSP UNIX domain sockets

❌ The Blocker: Mutex Lock & Missing Scan Config

Error: "/var/lib/gvm/feed-update.lock is locked by another process."

Error: "Failed to create a new Task because the default Scan Config is not available."

Why It Happened: When GVM starts, systemd fires an automated background sync. This background job creates a mutex lock file (feed-update.lock). If an engineer runs manual CLI commands during this window, the database deadlocks, preventing scan profiles (Full and fast) from compiling.

✅ The Solution: Graceful Lock Reset & Foreground Sync
# 1. Stop daemons to halt competing background threads kali@kali:~$ sudo gvm-stop # 2. Safely remove orphaned lock files kali@kali:~$ sudo rm -f /var/lib/gvm/feed-update.lock # 3. Verify UNIX domain socket ownership & start services kali@kali:~$ sudo gvm-start kali@kali:~$ ls -l /run/ospd/ospd-openvas.sock srwxrwx--- 1 _gvm _gvm 0 Oct 15 09:09 /run/ospd/ospd-openvas.sock

The Purpose: Eliminates race conditions between background and foreground threads, allowing gvmd to cleanly register default scan profiles.

🔑 Key Architectural Takeaway

Why NVTs Must Be Available First: In OpenVAS, a Scan Configuration is essentially a filtered query of Network Vulnerability Tests. If the NVT cache is empty, gvmd cannot compile the scan configuration. Once feeds sync completely in foreground mode, the Full and fast scan config becomes immediately available in the web UI.

✅ Empirical Engineering Justifications

Authoritative Answers to Committee Questions

Rigorous architectural, empirical, and database evidence resolving each evaluation inquiry

✅ Answer 1: Sensor vs. Management Plane

OpenVAS is merely an assessment sensor; it has zero concept of enterprise workflow, SLAs, or ticket lifecycles. It cannot deduplicate findings across recurring scans, cannot track which developer resolved a flaw, has no SLA timers, and cannot correlate network findings with web or code findings.

The Solution: DefectDojo provides the unified management, governance, and verification plane, converting dead XML artifacts into actionable, SLA-tracked engineering tickets.

✅ Answer 2: Relational Consistency & Mutex Locks

OpenVAS enforces strict relational consistency in PostgreSQL. A Scan Task requires a Scan Config, and a Scan Config is an SQL query over available NVTs.

If Greenbone permitted task creation while the feed was actively writing, scans would execute with incomplete vulnerability definitions, causing dangerous false negatives. Mutex locking (feed-update.lock) guarantees data integrity.

✅ Answer 3: Unified 'Assets' Taxonomy (v3.4.101)

Legacy models used 'Product Types' & 'Products', designed solely for software code repositories.

Version 3.4.101 introduces the Organization → Asset hierarchy. This allows infrastructure servers (like Target Lab Server at 10.0.2.15), subnets, and cloud VPCs to be modeled natively with technical owners, SLAs, and location reports.

✅ Answer 4: Deterministic SHA-256 Deduplication

DefectDojo computes a deterministic SHA-256 hash over the finding title, CVE, endpoint IP, and port.

When a subsequent scan is imported, matching hashes increment occurrence counters instead of creating duplicates. Missing findings are automatically transitioned from Active to Mitigated with historical audit trails preserved.

📋 Summary of Technical Architecture

By coupling native socket scanning with relational ASPM governance, our platform bridges the critical gap between active vulnerability discovery and verified remediation accountability—ensuring security issues are tracked, mitigated, and verified with zero manual spreadsheet overhead.
